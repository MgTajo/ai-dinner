# Your Superteam agent app

An app built with [Expo](https://expo.dev) (React Native + TypeScript), generated by **Superteam Agent Studio**. It runs **in your web browser** with nothing else to install, and the same code runs on Android. You don't need any blockchain or mobile experience.

## Quick start (in your browser)

You need [Node.js](https://nodejs.org) 20.19.4 or newer (22 LTS recommended). Check with `node -v`.

```bash
npm install
npm run web
```

Your browser opens the app at http://localhost:8081. Save a file and it reloads. To see it at phone size, open your browser's developer tools (right-click → Inspect) and switch on the device toolbar (the phone icon).

**The terminal will look like it's doing nothing** after it prints the address: that's normal. It is a server waiting for the browser. Leave it running and stop it with Ctrl+C.

### On Android (optional)

Run `npm start` instead. A QR code appears; install **Expo Go** from the Play Store, open it and scan the code (same Wi-Fi as your computer). Or start an Android Studio emulator and press `a`.

| Command | What it does |
| --- | --- |
| `npm run web` | Runs the app in your browser |
| `npm start` | Starts the Expo dev server and shows the QR code for a phone |
| `npm run android` | Same, and opens the app on a connected Android emulator or phone |
| `npm run typecheck` | Checks TypeScript types |
| `npm run build:web` | Builds the browser version into `dist/`, ready to host (Vercel, Netlify, any static host) |
| `npm run build` | Bundles the app's JavaScript for Android into `dist/` (a quick "does it compile" check; it does not make an installable APK) |

To make an installable APK or a Play Store build, use [EAS Build](https://docs.expo.dev/build/setup/) (`npx eas-cli build -p android`).

## Keeping secrets secret

**Never put an API key or wallet key in the app.** Everything inside an app, including any `EXPO_PUBLIC_` variable, can be read by anyone who installs it. Features that need a secret run in a small **companion server** in `companion-server/`, which keeps the keys and does the work. The app only calls that server.

## Project layout

```
app/              one file per screen (expo-router): app/index.tsx is the home screen
components/       shared UI pieces (Screen, Card, Button, …)
lib/              helpers for each feature; lib/companion.ts calls the companion server
app.json          app name, Android package id and other settings
studio.manifest.json   what Agent Studio generated, for reference
```

To add a screen, create `app/hello.tsx` and link to it with `<Link href="/hello">`:

```tsx
import { Text } from "react-native";

export default function Hello() {
  return <Text>Hello!</Text>;
}
```

## Companion server (`companion-server/`)

Some features in this app need secrets (a Gemini API key, a devnet wallet key). Those can't live in the app, so Agent Studio added a **companion server**: a small Node.js service in `companion-server/` that holds the keys and does that work. The app calls it over HTTP. It has its own README, `.env.example` and `package.json`.

**Run both** (two terminals):

```bash
# terminal 1: the companion server
npm run companion:install         # once: installs companion-server's packages
cp companion-server/.env.example companion-server/.env.local   # then fill it in (see companion-server/README.md)
npm run companion                 # starts it on port 3000

# terminal 2: the app
npm run web                       # or npm start for a phone
```

Each terminal prints one line (for example `Listening on http://localhost:3000`) and then waits: that's normal, leave both running.

**How the app finds it:** in the browser, the app calls http://localhost:3000. On a phone, it calls port 3000 on the computer running `npm start` (the address Expo already uses for the QR code). Check it from your phone's browser: `http://<your computer's IP>:3000` should answer with JSON. If it doesn't, your computer's firewall may be blocking port 3000, or the phone is on a different Wi-Fi.

**Port 3000 already in use?** (for example by another project): start the companion on another port with `PORT=3300 npm run companion`, and point the app at it in this app's `.env.local`: `EXPO_PUBLIC_COMPANION_URL=http://10.0.2.2:3300` on the Android emulator, or `http://<your computer's IP>:3300` on a phone. Then restart `npm start`. The home screen's **Companion server** light shows ONLINE once the app can reach it.

**For a release build:** deploy `companion-server/` to any Node.js host (see its README), then set `EXPO_PUBLIC_COMPANION_URL=https://your-server.example.com` in this app's `.env.local` before building. Android release builds only allow `https://`. If you host the browser version too, add its address to the companion's `.env.local` as `CORS_ALLOW_ORIGIN=https://your-app.example` so browsers let it call the server.

> ⚠️ The companion's endpoints have no login. Anyone who can reach it can use your Gemini quota or make its agent spend its (devnet, test-money) budget. Add authentication before you share it widely.

## Gemini AI

**What you get:** a **Gemini chat** screen (`app/chat.tsx`). It sends your question to the companion server's `POST /api/chat`, which asks Google Gemini with the official [`@google/genai`](https://www.npmjs.com/package/@google/genai) SDK. The Gemini key stays in `companion-server/.env.local`, never in the app.

**Setup (2 minutes, free):**

1. Go to https://aistudio.google.com/apikey and sign in with a Google account.
2. Click **Create API key** and copy it.
3. In **`companion-server/.env.local`** (not the app's) set `GEMINI_API_KEY=your-key`, then restart `npm run companion`.

**Try it:** open the app, tap **Gemini chat**, ask a question.

**Code:** `lib/ai/client.ts` (the app side) and `companion-server/src/routes/chat.ts` + `companion-server/src/lib/ai/gemini.ts` (the server side).

**If it fails:** "Can't reach the companion server" means `npm run companion` isn't running or your phone can't reach your computer (see *Companion server* above). "GEMINI_API_KEY is not set" means `companion-server/.env.local` is missing the key or you didn't restart the companion. Anything else: the terminal running `npm run companion` shows the reason (often an invalid key or a free-tier rate limit).

## Internet-native payments (x402 on Solana devnet)

**What it is:** [x402](https://www.x402.org) brings back the HTTP status code `402 Payment Required`. A server answers "this costs $0.01"; the caller pays and repeats the request; the server checks the payment and responds. No sign-ups, cards or API keys. Programs (like AI agents) can pay for things on their own.

**No real money.** Only **Solana devnet** (a test network with free, worthless tokens) is allowed. The companion server refuses any other network on purpose.

**Where it runs:** charging and paying both happen in the **companion server**, because paying needs a wallet key and a key inside an app can be extracted. The app only reads prices: `lib/payments/client.ts` has `checkPrice(path)`, which calls a companion endpoint without paying and decodes the `PAYMENT-REQUIRED` header (base64 JSON: network, token, amount, receiving address).

**Setup:** follow *Internet-native payments* in **`companion-server/README.md`**. Run its commands inside that folder:

```bash
cd companion-server
npm run keygen -- --pay-to   # where payments arrive (seller)
npm run keygen               # the companion's own agent wallet (buyer)
npm run wallets              # after getting faucet USDC: should show ✓ for both
```

> ⚠️ `AGENT_PRIVATE_KEY` lives only in `companion-server/.env.local`. Never copy it into the app or an `EXPO_PUBLIC_` variable.

To let *people* pay from their own wallet app (instead of the companion's agent), add the **Wallet Connection** module: it uses Solana Mobile Wallet Adapter and needs a development build.

## AI Race adapter

**What you get:** your **companion server** answers the two endpoints the AI Race verifier calls, `GET /agent-studio/v1/health` and `POST /agent-studio/v1/tasks`, already speaking the race protocol (ASRP/1): token check, nonce echo and the answer envelope. A **Race readiness** screen (`app/race.tsx`) shows what the verifier will find. The verifier tests the companion server, not the phone.

**What you build:** the AI logic, one function per task type in `companion-server/src/race/handlers.ts`. Each race layer tests one capability (answering with a model, structured output, tool calling, knowledge, memory, reliability, workflows). They start as "not built yet" and return a clear error until you write them. `companion-server/src/race/tools.ts` has `callTool` and `searchSource`.

**Setup:**

1. On Agent Studio, open your team page and copy the **verifier token** into **`companion-server/.env.local`** as `AGENT_STUDIO_VERIFIER_TOKEN`, then restart `npm run companion`.
2. Write `handlers.respond` (the first layer), for example with the Gemini module: `respond: async (task) => ({ text: await askGemini(String(task.input)) })` using `../lib/ai/gemini.js`.
3. Try it: in `companion-server/`, run `npm run race:try -- respond "What is 6 x 7?"`.
4. Deploy the companion server (Railway, Render, Fly…) or run a tunnel, and paste its public https:// URL on your team page. Then press **Run verification** on the race page.

**Memory on serverless hosting:** the Memory and Context layer checks that your companion server remembers earlier turns. If you deploy it to a serverless host (such as Vercel), history kept in a variable is lost between turns. Use `memory` from `companion-server/src/race/memory.ts` and set `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` from a free Upstash Redis database (on Vercel, Storage → Upstash for Redis adds `KV_REST_API_URL` and `KV_REST_API_TOKEN`, which also work). On an always-on server (Railway, Render, Fly) the in-process fallback is fine.

**Tests:** in `companion-server/`, `npm run test:race` checks the protocol handling offline. The race verifier checks your AI logic with fresh inputs on every attempt.

## Spending controls

The agent that pays runs in the companion server, so its limits do too, next to the key they protect. Limits enforced inside an app could be switched off by whoever installs it. Before every payment the companion checks:

- **Per-payment cap** (`MAX_PAYMENT_USD`, default `0.10`): anything more expensive is refused before it is signed.
- **Total budget** (`AGENT_BUDGET_USD`, default `1.00`): once this much has been spent, further payments are refused.
- **Only devnet USDC**: prices in any other token are refused.

Set them in `companion-server/.env.local`. The running total resets when the companion restarts. Details and code: *Spending controls* in `companion-server/README.md`.

**Test it (no wallet needed):** `cd companion-server && npm run test:spending`

## Paid API example

**What you get:**

- In the companion server: `GET /premium-data`, an endpoint that costs `$0.01` (devnet USDC) per call, and `POST /api/buy`, the companion's own agent that buys it within its spending limits. Change the price with `PAID_API_PRICE_USD` in `companion-server/.env.local`, and replace the handler in `companion-server/src/routes/premium-data.ts` with whatever you want to sell.
- In the app: a **Premium data** screen (`app/premium.tsx`, using `lib/paidapi/client.ts`). **Check the price** calls `/premium-data` without paying and shows the decoded `PAYMENT-REQUIRED` price. **Let the agent pay** calls `POST /api/buy` and shows the data, the receipt and the remaining budget.

**Try it:** finish the payments setup in `companion-server/README.md`, start `npm run companion`, open the app and tap **Premium data**. Without funded wallets, step 2 shows the facilitator's reason (usually "insufficient funds") and the budget is not charged.

A successful payment shows a `receipt` with a `transaction` id. Paste it into https://explorer.solana.com/?cluster=devnet to see it on-chain.

**If it fails:** the *Paid API example* table in `companion-server/README.md` lists every message and its fix. Run those commands inside `companion-server/`.

## Pay.sh

**What it is:** [Pay.sh](https://pay.sh) is a free, open-source tool from the Solana Foundation. Its `pay` command pays HTTP 402 charges for you, using the same x402 protocol as your companion server. It keeps its own wallet on your computer, so nothing about it goes into the app.

**Where it runs:** on your computer, against the companion server. Install it once with `brew install pay` (macOS) or `npm install -g @solana/pay`, then follow *Pay.sh* in **`companion-server/README.md`**. Run its commands inside that folder:

```bash
cd companion-server
npm run paysh              # pays the companion's GET /premium-data once from your Pay.sh wallet
npm run paysh -- wallet    # shows that wallet's devnet address and USDC balance
```

**Let Claude Code use your API:** run `pay claude` in `companion-server/`. Claude Code can then pay for the companion's paid endpoints while it helps you build.

## Wallet Connection

> **Android only.** Mobile Wallet Adapter connects to a wallet app on an Android phone, so this screen doesn't work in the browser version (`npm run web`); the rest of the app does.

**What you get:** a **Pay with your wallet** screen (`app/wallet.tsx`). People connect a Solana wallet app that is on the same phone (Phantom, Solflare, Backpack, …) and pay the companion's `GET /premium-data` from it. The wallet shows every payment, and they approve or reject it there. The app never sees a key.

**How it works:** [Solana Mobile Wallet Adapter](https://docs.solanamobile.com) (`@solana-mobile/mobile-wallet-adapter-protocol-kit`, maintained by Solana Mobile) opens the wallet app. `lib/wallet/mobileWallet.ts` turns the connected wallet into a `@solana/kit` signer, and `lib/wallet/pay.ts` gives that signer to the same x402 client the web template uses. The x402 facilitator pays the network fee, so the wallet only needs devnet USDC, not SOL. React Native has no WebCrypto, which `@solana/kit` uses for SHA-256, so `lib/wallet/crypto-polyfill.ts` provides it from Expo's own `expo-crypto`.

**This needs a development build, not Expo Go.** Mobile Wallet Adapter is native Android code, which Expo Go can't load. Build your own version of Expo Go once:

```bash
npm run android:dev    # builds and installs the app on a running emulator or a USB-connected phone (first build: 5 to 15 minutes)
```

After that, `npm start` works as before and the app reloads when you save. Run `npm run android:dev` again only when you add a native package. You need [Android Studio](https://developer.android.com/studio) (for the Android SDK and an emulator) and Java 17.

**Try it:**

1. Finish the payments setup in `companion-server/README.md` and start `npm run companion`.
2. Install a wallet app with Mobile Wallet Adapter on the phone or emulator, switch it to **devnet**, and send its address devnet USDC from https://faucet.circle.com.
3. Open **Pay with your wallet** in the app: **Connect wallet**, approve in the wallet, then **Buy premium data** and approve the payment.

A successful payment shows a transaction id. Tap it to see it on the Solana Explorer (devnet).

**If it fails:**

| Message | Fix |
| --- | --- |
| `No Solana wallet app found on this phone` | Install a wallet with Mobile Wallet Adapter (Phantom, Solflare, Backpack) |
| `insufficient_funds` or `simulation_failed` | The wallet has no devnet USDC yet: use the faucet. The companion's seller address needs a USDC account too (see the payments setup) |
| The app crashes with `SolanaMobileWalletAdapter` not found | You are in Expo Go. Use the development build: `npm run android:dev` |
| `You declined in the wallet` | Nothing was paid. Try again and approve |

Android only: Mobile Wallet Adapter doesn't exist on iOS.
